Splice Handoff Broker

Design notes and test evidence for handing a long-running agent task from one process to another without running it twice. Version 0.2.4.

This page is a write-up. The broker itself does not run on this page, and the package is not offered for download here. The test results below come from the author's own runs of the test suites shipped with the package.

The problem

Long agent sessions die mid-task. The usual recovery is a person copying context into a new session and hoping the old one is really gone. Three failures follow:

  1. Both run at once. The old process wakes up and writes the same result again.
  2. Handoff "completed" but nobody took over. A message was delivered into the void.
  3. Context silently truncated. A summary keeps the last few turns and drops the acceptance criteria from an hour ago.

Splice handles the first two mechanically. For the third it makes the loss visible: the snapshot is the executor's own structured state, content-addressed with sha256 and immutable, so what was handed over can be re-read and compared later. It does not make the snapshot complete. What goes into it is the executor's decision.

The design in one picture

Handoff is treated as a transaction, not a message:

archive→claim→acknowledge→ownership moves
  • A fence is checked on writes. A write carrying a stale fence is rejected, so a replaced executor is locked out mechanically.
  • Ownership moves at the ack, not at the claim. A crash between claim and ack leaves the task recoverable by a third executor.
  • Every step carries an idempotency key. A retried step is recorded at most once.
  • Every transition goes into a hash-chained audit log that can be verified afterwards.

Where the idea comes from

Handing ownership between processes safely is not new. The core mechanism is the fencing token described by Martin Kleppmann in How to do distributed locking (2016): each time a lock changes hands it carries a number that only increases, and the resource rejects requests carrying an older number.

What Splice adds around that idea: the handoff is a four-step transaction (archive, claim, acknowledge, ownership moves), so a crash between claim and ack leaves the task recoverable. Snapshots are content-addressed with sha256 and checked on read. Every transition goes into a hash-chained audit log. Each step carries an idempotency key, so a retried step is recorded once.

What it does not add: fencing covers writes that pass through the broker. A stale process can still call an external system directly. That gap needs conditional writes or idempotency keys at the destination, and a broker cannot close it for you. The package says the same: your effect must be applied under the same key.

Protocol at a glance

States: active → handoff_pending → handed_off → completed.

Every write carries a holder and a fence. A write is accepted only when the fence equals the task's current epoch and that holder owns a live lease. Any ownership transfer increments the epoch, so the previous owner's writes fail instead of racing.

StepCallEffect
archivePOST /v1/tasks/{id}/handoffStores the snapshot by sha256, bumps the epoch, clears owner and lease, state becomes handoff_pending
claimPOST /v1/handoffs/{id}/claimNew executor takes a lease, bumps the epoch again, receives the snapshot
ackPOST /v1/handoffs/{id}/ackState becomes handed_off
workPOST /v1/tasks/{id}/writeFenced writes, deduplicated by idempotency_key

Also: POST /v1/tasks (create), /lease, /takeover and /complete on a task; GET on tasks, handoffs, /v1/audit, /v1/audit/verify, /v1/health, /v1/protocol.

Guarantees and how each one is checked

GuaranteeMechanism
An executor that lost ownership can never write againFence checked on writes; a stale fence is rejected (409 stale_fence)
A retried step never executes twiceIdempotency key; a repeated key reports deduplicated
A snapshot cannot be silently corruptedContent-addressed with sha256; a tampered snapshot is rejected on read
Handoff is not "message sent"archive, claim, ack, then ownership
A crashed executor does not block the task foreverLease TTL and takeover
Every transition is auditableHash-chained audit log

The package is not offered for download on this page. If you hold it, extract it and run one command from the extracted folder:

bash tools/run_tests.sh

It runs the three suites above and prints RESULT: ALL GREEN or RESULT: FAIL. It is fail-closed: a missing test file exits 2 and a failing suite exits 1. It needs Python 3.10+, Node 18+ and OpenSSL, and it needs no external network or external service (the tests use a local 127.0.0.1 broker). It writes under out/ and tests/tls/ in the package folder, plus a log at /tmp/splice_run.out and temporary splice-e2e-* state directories in the system temp directory. Author runs used CPython 3.10.12 and Node 22.

What it is not

Scope limits stated by the package itself
  • Not a task queue or a workflow engine. It moves ownership of one task between executors. Scheduling stays where you already do it.
  • Not a context store for the model. Splice makes the snapshot immutable and verifiable, not complete.
  • No adapter for any vendor agent runtime. Nothing has been validated against a specific runtime's session model.
  • No clustering. One broker owns the SQLite file.
  • No UI. Operations are HTTP plus the audit log.
  • No exactly-once delivery into your own system. Splice records each idempotency key at most once; your effect must be applied under that key.
  • TLS termination and bearer-token auth are supported. You bring the certificate; the broker does not issue or rotate certificates.
  • No automatic retry scheduler. A dead executor is recovered by lease expiry and takeover, which you or your supervisor must trigger.
  • Windows is untested.
